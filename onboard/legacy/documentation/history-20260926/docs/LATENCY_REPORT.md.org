# ARGUS 비전 파이프라인 지연 분포 정밀 측정 — C++ 포팅 판단 자료

> 2026-09-26 변경: 현재 코드는 전체 박스만 사용한다. 아래 성능 기록은 하단 ROI 후처리가 있던 과거 코드의 측정값이며, 변경 후 재측정값이 아니다.

## 0. 측정 목적과 가설

`hailortcli run`으로 잰 Hailo-8 NPU 단독 성능은 **147 FPS, HW Latency 6.27ms**다. 그런데 Python 파이프라인(`vision_node.py`)을 통해 같은 HEF를 돌리면 프레임당 10~14ms, 변동폭이 40%에 달했다. 이 문서는 그 차이의 정체를 프레임 단위로 분해 측정해서, **C++로 포팅했을 때 실제로 얼마나 개선될지 수치로 근거를 남기기 위한 자료**다.

측정 전 세운 가설 두 가지:

- **가설 1**: NPU 대기 구간(`hw_wait_ms`)을 따로 떼어 재면 6.27ms에 가까울 것이고, 그 차이(≈4~5ms)가 곧 "파이썬 계층 비용"일 것이다.
- **가설 2**: 큐(`LatestFrameQueue`)를 거치면서 생기는 지연은 락 경합이나 스레드 깨우기 지연 때문일 것이다.

결론부터 말하면 **두 가설 모두 데이터로 기각되었다.** 아래에서 어떻게 기각됐는지, 그럼 실제 원인이 뭔지 순서대로 규명한다.

### 측정 방법

`vision_node.py --latency-csv <경로>`(옵션, 기본 꺼짐)로 프레임별 구간을 `time.perf_counter_ns()`로 기록하고, 종료 시 1회 CSV 기록 + 통계 출력. 환경: Raspberry Pi 5, HailoRT 4.23.0, `yolox_s_leaky_hailo8_zoo_v2.19.0.hef`(80클래스, HailoRT NMS 내장).

| 조건 | 입력 | 옵션 | processed | 성격 |
|---|---|---|---|---|
| A | test.mp4(합성 640x480) | 기본(비동기, queue=2) | 190 | 처리 능력을 몰아붙이는 스트레스 조건 |
| B | 웹캠 실시간 | 기본(비동기, queue=2) | 578, 드랍 0 | 카메라가 병목인 현실 조건 |
| C1/C2 | test.mp4 | `--publish-npu-input` 끔/켬 | 189/203 | GIL 경쟁 검증 |
| D | test.mp4 | `--disable-gc` | 201, GC 0건 | GC 영향 검증 |
| **E(신규)** | test.mp4 | `--backend hailo-sync`(동기 API) | 202 | **비동기 구조 vs GIL, 원인 분리** |
| **F(신규)** | test.mp4 | `--frame-queue-size 1` | 210 | **큐 정체 규명** |

## 1. 가설 1 기각: `hw_wait_ms`는 6.27ms에 가깝지 않다

7개 조건 전부에서 `hw_wait_ms`가 6.27ms보다 **44~60% 높다**(mean 9.0~10.8ms). "6.27ms 근처면 나머지가 파이썬 비용"이라는 전제 자체가 성립하지 않는다 — **`hw_wait_ms`라는 이름의 구간 안에 이미 파이썬 비용이 섞여 있다.**

### 원인 규명 실험: 비동기(Event) vs 동기(`run()`) 직접 비교

`hw_wait_ms`는 `wait_for_async_ready()` + `run_async()` 디스패치 + `done.wait()`(파이썬 `threading.Event`) + `last_job.wait()`를 전부 포함한다. 이 구조 자체(콜백+Event) 때문에 느린 건지, 아니면 파이썬에서 Hailo를 호출하는 행위 자체가 원래 이만큼 걸리는 건지 분리하기 위해, **HailoRT의 동기 API `ConfiguredInferModel.run(bindings, timeout_ms)`(블로킹, 콜백/Event 없음)로 바꾼 `HailoNmsDetectorSync`를 별도 클래스로 추가**(`--backend hailo-sync`, 원본 `HailoNmsDetector`는 그대로 둠)해서 같은 test.mp4로 측정했다.

| | A: 비동기(run_async+Event) | E: 동기(run()) | 차이 |
|---|---|---|---|
| hw_wait mean | 10.027ms | **9.915ms** | -0.112ms (오차범위) |
| hw_wait p99 | 11.932ms | **11.158ms** | -0.774ms (오차범위) |
| infer_total mean | 10.965ms | 10.908ms | -0.057ms |

**결론**: 동기 API로 바꿔도 `hw_wait_ms`는 전혀 줄지 않았다(오히려 근소하게 더 좋았지만 런 간 잡음 수준). **콜백+Event 구조 자체의 문제가 아니라, 파이썬이 HailoRT를 호출하고 결과를 기다리는 행위 자체에 GIL/OS 스케줄링 비용이 고정적으로 붙는다는 뜻이다.** 동기든 비동기든 파이썬 인터프리터가 "무언가를 기다렸다가 깨어나는" 순간마다 이 비용이 발생하므로, API 스타일을 바꾸는 것으로는 해결이 안 되고 **인터프리터/GIL 자체를 벗어나야(C++ 포팅) 없앨 수 있는 비용**이라는 게 실험으로 확인됐다.

## 2. 가설 2 기각: 큐 지연은 락 경합도, 스레드 깨우기 지연도 아니다

이전 보고서에서 `total_ms - 구간 합`으로 역산했던 "큐 대기 2.7ms"는 근거가 약했다. 이번엔 **캡처 스레드가 `put()`한 시각과 메인 스레드가 `get()`으로 실제 꺼낸 시각을 각각 직접 기록**하고, `put()`/`get()` 호출 자체가 걸린 시간도 별도로 측정했다.

| | put() 호출 자체 (생산자, 락+eviction) | get() 호출 자체 (소비자, 대기 포함) | 실제 큐 체류(put→get) |
|---|---|---|---|
| **A (queue=2, test.mp4)** | mean 0.035ms, max 0.66ms | mean 0.031ms, **200개 중 199개는 블로킹 없음** | **mean 2.59ms**, p99 3.60ms |
| **B (queue=2, 웹캠)** | mean 0.028ms | mean **55.5ms**(카메라 기다리는 정상 대기) | mean **0.06ms** |
| **F (queue=1, test.mp4)** | mean 0.038ms | mean 0.032ms, 거의 안 블로킹 | mean **1.27ms** |

- `put()`/`get()` **호출 자체는 어느 조건에서도 0.03~0.04ms**로 무시할 수준 → **락 경합 아님.**
- test.mp4(생산자가 소비자보다 훨씬 빠른 스트레스 조건)에서 `get()`이 실제로 블로킹 대기한 경우는 200개 중 1개뿐 → **스레드 깨우기(condition variable wait) 지연도 아님.** (웹캠 조건의 55.5ms는 "카메라가 다음 프레임 줄 때까지 정상적으로 기다린 시간"이라 문제가 아니다.)
- 그런데도 test.mp4에서 큐 체류가 **평균 2.59ms**나 나온다. **큐 용량을 2→1로 줄이자(F) 체류가 1.27ms로 거의 정확히 절반이 됐다.**

**결론**: `LatestFrameQueue`(`queue.Queue` 래퍼, 용량 2)는 FIFO다. 생산자가 소비자보다 훨씬 빠르면, `put()`이 가득 찬 큐에서 가장 오래된 1개만 지우고 새 걸 넣기 때문에, 어느 순간이든 큐 안에는 "직전 프레임"과 "그 이전 프레임" 두 개가 같이 들어있을 수 있고 `get()`은 그중 **더 오래된 쪽(FIFO 앞쪽)**을 돌려준다. 이게 락도 아니고 깨우기 지연도 아닌, **큐 용량(capacity) 자체의 구조적 지연**이다. 용량을 1로 줄이면 이 "한 칸 밀림"이 사라져서 체류가 절반으로 줄어드는 걸 직접 확인했다(부가 소득: `--frame-queue-size 1`이 총 지연도 소폭 낮춘다 — total mean 16.6ms vs 17.0ms).

## 3. 최종 지연 분해 — NPU 고유 / 스레드 동기화 / 실제 연산

웹캠(B, 카메라가 병목인 가장 현실적인 조건, 드랍 0) 기준:

```
NPU 고유 실리콘 처리            ≈  6.27 ms  (고정, hailortcli 벤치마크 기준, 언어 무관)
+ 파이썬↔HailoRT 호출 동기화 비용 ≈  2.72 ms  (hw_wait 9.0ms - 6.27ms; 1장에서 GIL/스케줄링 기인으로 특정)
+ input_copy + output_fetch      ≈  0.53 ms  (Hailo 파이썬 바인딩 오버헤드)
+ nms_parse                      ≈  0.30 ms  (파이썬 루프)
+ preprocess(letterbox)          ≈  1.30 ms  (OpenCV 호출 + numpy 왕복)
+ postprocess(hull)              ≈  0.04 ms
+ publish(msgpack+zmq)           ≈  0.16 ms
+ 큐 체류(FIFO 구조, 2장)         ≈  0.06 ms  (카메라 병목 조건이라 거의 0)
──────────────────────────────────────────────
total_ms (mean, 실측)            ≈ 11.4 ms
```

test.mp4처럼 생산자가 소비자보다 빠른 조건에서는 여기에 큐 체류 ≈2.6ms(용량 2 기준)가 추가로 붙어 total_ms가 17ms대로 올라간다.

**"NPU 고유"(6.27ms)를 뺀 나머지 전부(약 5.1ms, 웹캠 기준)가 파이썬 계층 비용**이며, 그중 절반 이상(2.72ms)이 눈에 보이는 전처리/후처리가 아니라 **"하드웨어를 기다린다"는 이름 뒤에 숨은 GIL/스케줄링 비용**이라는 게 이번 측정의 핵심이다.

## 4. GIL 경쟁의 직접 증거 (`--publish-npu-input` on/off)

같은 test.mp4로, 인코딩 스레드만 켜고 끄고 비교(재현성 확인을 위해 2회 반복, 두 라운드 모두 방향·크기 일치):

| | 끔 | 켬 | 차이 |
|---|---|---|---|
| hw_wait mean | 10.37ms | 10.82ms | **+4.4%** |
| hw_wait p99 | 13.92ms | 15.67ms | **+12.6%** |
| infer_total mean | 11.30ms | 11.85ms | +4.9% |
| total mean | 17.32ms | 18.47ms | +6.7% |

인코딩 스레드가 하는 일(`cv2.cvtColor`+`cv2.imencode`+zmq 송신)은 NPU와 무관하다 — **Hailo 칩은 다른 파이썬 스레드가 뭘 하든 항상 같은 시간에 연산을 끝낸다.** 그런데도 `hw_wait_ms`(정의상 "파이썬이 완료를 알아차리는 시각까지")가 늘어났다는 건, **인코딩 스레드가 CPU/GIL을 쓰는 동안 메인 스레드가 깨어나 리턴하기까지 더 기다려야 했다는 뜻**이다. 이게 GIL/스케줄링 경쟁의 직접 증거다 — 겉보기엔 "하드웨어 대기"라는 항목이 늘었지만, 실제론 파이썬 스레드 스케줄링 문제다.

## 5. GC는 원인이 아니다

- `gc.disable()`은 **순환 참조 수집기만 끈다.** numpy 배열, `slots=True` 데이터클래스(`Detection`/`DetectionFrame`) 등은 참조 카운팅으로 즉시 해제되며 GC와 무관하다.
- 실측: GC 켠 조건들에서 200개 프레임 처리 동안 GC 이벤트가 **0~1건**(0.09~0.15ms)뿐이었고, p95 outlier와 겹친 적은 총 7개 조건 중 1건(A2, 10개 중 1개)뿐이었다.
- `gc.disable()`(D2) 결과: total p99 = 20.74ms — GC 켠 조건들(A2 20.73ms, C1b 24.38ms)과 비교해 뚜렷한 개선이 없다.
- **결론**: 이 핫패스(캡처→전처리→추론→발행)는 순환 참조를 거의 만들지 않는 구조(짧게 살고 죽는 배열/불변 객체)라서, 애초에 GC gen2 스캔이 자주 돌 재료가 적다. C++ 포팅으로 GC를 완전히 없앨 수 있지만, **이 워크로드 기준으로는 그 이득이 측정 가능한 수준이 아니다.**

## 6. C++ 포팅 시 개선 기대 구간과 예상 효과 (수치)

| 구간 | 현재 값(웹캠 mean) | 포팅 기대 | 예상 효과 | 근거 |
|---|---|---|---|---|
| NPU 고유 처리 | 6.27ms | **없음** | 0ms | 물리적 하드웨어 한계, hailortcli 기준값 자체 |
| **하드웨어 대기 중 GIL/스케줄링분** | 2.72ms | **가장 큼** | **-2~2.7ms** | 1장: 동기/비동기 무관하게 발생 → C++ 네이티브 대기(조건변수, GIL 없음)로 대부분 제거 가능 |
| input_copy + output_fetch | 0.53ms | 개선 | -0.3~0.5ms | 파이썬 바인딩 계층 제거, HailoRT C++ API 직접 호출 |
| nms_parse | 0.30ms | 개선(절대값 작음) | -0.2ms | 인터프리터 루프 vs 네이티브 루프 |
| preprocess(letterbox) | 1.30ms | 부분 개선 | -0.3~0.7ms | OpenCV 자체는 C++이지만 numpy 객체 할당/왕복 비용 존재 |
| postprocess(hull) | 0.04ms | 미미 | 0ms | 이미 무시 가능한 수준 |
| publish(msgpack+zmq) | 0.16ms | 소폭 개선 | -0.05ms | zmq는 이미 C 라이브러리, msgpack 직렬화만 개선 여지 |
| 큐 체류(FIFO 구조) | 0.06~2.6ms(부하 의존) | 코드 수정으로 즉시 개선(포팅 불필요) | -1.3ms(용량 2→1) | 2장: 언어와 무관, 큐 설계 문제 |
| GC | 0~1건, <0.15ms | 완전 제거 가능하나 | 측정상 0ms | 5장: 이 워크로드에서 영향 없음 |

**총 예상 개선폭**: 웹캠 조건(total mean 11.4ms) 기준 **약 2.5~4.2ms**(22~37%) 단축 예상 — 대부분 "하드웨어 대기" 항목 안에 숨어있던 GIL/스케줄링 비용에서 나온다. NPU 고유 6.27ms는 그대로 남으므로, **C++로 포팅해도 이론적 하한은 여전히 약 7~8ms대**(NPU 6.27ms + 남는 최소 오버헤드)이지 0에 가까워지지는 않는다.

## 7. 한계 (측정 신뢰도 관련 유의사항)

- **측정 경계 문제**: `hw_wait_ms`는 "파이썬이 완료를 알아차린 시각"이지 하드웨어 자체의 완료 시각이 아니다. `hailortcli`의 6.27ms는 다른(아마도 더 저수준/폴링 기반) 측정 방식일 가능성이 있어 **완전히 동일한 정의의 값끼리 비교한 게 아니다.** 그래도 "6.27ms에 가깝지 않다"는 방향성 자체는 여러 조건에서 일관되게 재현됐다.
- **표본 수**: test.mp4 조건들은 프레임 190~210개(2.7~3.2초), 웹캠은 578개(38초) — 통계적으로 크지 않다. p99/max는 표본이 적을수록 잡음에 민감하다.
- **런 반복 없음**: 각 조건을 1회씩만 측정했다(재현성 확인용으로 A/C1/C2만 두 라운드 반복). 표준오차·신뢰구간을 계산하지 않았고, 열적 상태(써멀 스로틀링)나 스케줄링 잡음이 런마다 다를 수 있다.
- **동기 API 비교(1장)의 한계**: `ConfiguredInferModel.run()`도 결국 파이썬 함수 호출이라 GIL 재획득 자체는 피할 수 없다 — "완전히 GIL 밖에서 대기"하는 C 확장 콜백 방식과는 다르다. 즉 이 실험은 "비동기 vs 동기"를 비교한 것이지 "파이썬 vs 비-파이썬"을 비교한 게 아니다. C++로 직접 포팅했을 때의 진짜 개선폭은 이 실험이 아니라 실제 포팅 후 재측정으로만 확정할 수 있다.
- **`--disable-gc` 실험(5장)**: GC 이벤트 자체가 워낙 적어(0~1건) "GC가 없다"는 결론의 통계적 근거가 약하다. 더 긴 시간(수분 이상) 돌려서 gen1/gen2 컬렉션이 누적되는 조건에서 재검증하면 결론이 달라질 수 있다.
- **큐 실험(2장)의 일반화 한계**: 용량 1로 줄이면 지연은 줄지만 **드랍률이 늘 수 있는 트레이드오프**가 있다(이번 표본에서는 오히려 처리량이 비슷했지만, 카메라 프레임레이트가 더 높은 환경에서는 다를 수 있다).
