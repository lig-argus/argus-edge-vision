# ARGUS RPi5 Hailo8 YOLOX 시스템 이해 및 구현 가이드

> 2026-09-26 후속 변경: 입력 팩토리·시각 계약·오류 전달·트랙 TTL 및 버스 종료를 수정했다. 현재 구조는 DESIGN_ALIGNMENT.md와 상위 README를 기준으로 확인한다. 이 문서의 이전 실험 결과는 재측정값이 아니다.

버전 1.0  
대상 시스템 Raspberry Pi 5 Hailo 8 RGB 카메라 YOLOX 자체 Pub Sub 버스  
기준 구현 `argus_vision_bus`

## 이 문서의 목적

이 문서는 Raspberry Pi 5에 연결한 640×480 RGB 카메라 영상을 Hailo-8에서 YOLOX로 탐지하고, ROS 2 없이 자체 메시지 버스로 탐지 결과를 전달하는 전체 구조를 설명한다. 카메라 프레임 한 장이 어디에서 만들어지고, CPU와 NPU가 각각 무엇을 처리하며, 어떤 데이터가 버스를 통해 추적기와 통제기로 전달되는지를 순서대로 다룬다.

현재 코드에서 바로 실행할 수 있는 범위는 카메라 입력, 최신 프레임 큐, 영상 전처리, Hailo-8 추론, 전체 박스 좌표 복원, ZeroMQ 발행, 탐지 결과 구독 및 선택적 JPEG 미리보기까지다. ByteTrack 추적, PX4 비행 제어, Windows 통제기, 명령 응답과 안전 제어는 다음 구현 단계다. 이 구분을 이해하면 이미 동작하는 기능과 앞으로 만들어야 할 기능을 혼동하지 않는다.

## 먼저 알아야 할 핵심

카메라와 Hailo-8은 같은 일을 하지 않는다. 카메라는 픽셀 배열을 만들고, CPU는 픽셀 배열을 모델 입력 형태로 바꾸며, Hailo-8은 객체의 위치와 점수를 숫자로 반환한다. CPU가 그 숫자를 원본 영상 좌표로 복원해 메시지 버스로 발행한다.

```text
640×480 RGB 카메라 영상
        ↓
CPU 전처리와 640×640 Letterbox
        ↓
Hailo-8 YOLOX 추론과 NMS
        ↓
객체 클래스 신뢰도 박스 좌표
        ↓
전체 박스 좌표와 시간 정보 추가
        ↓
ZeroMQ와 MessagePack으로 발행
        ↓
Tracker 통제기 Recorder가 구독
```

NPU 출력은 박스가 그려진 영상이 아니다. 예를 들어 사람 한 명을 찾았을 때 NPU는 `사람`, `0.92`, `x1 y1 x2 y2`에 해당하는 숫자를 반환한다. 박스 그리기와 화면 전송은 CPU와 UI가 담당한다.

## 전체 아키텍처

```mermaid
flowchart LR
    CAM[RGB 카메라 640x480] --> CAP[Frame Source]
    CAP --> Q[최신 프레임 큐]
    Q --> PRE[Letterbox RGB 변환]
    PRE --> NPU[Hailo 8 YOLOX NMS]
    NPU --> POST[원본 좌표 전체 박스]
    POST --> PUB[Observation Publisher]
    PUB --> BUS[ZeroMQ Bus]
    BUS --> TRACK[Tracker 다음 단계]
    BUS --> UI[Windows UI]
    BUS --> LOG[Recorder]
    TRACK --> CTRL[ControlLoop 다음 단계]
    CTRL --> MAV[MAVSDK Vehicle Adapter]
    MAV --> PX4[PX4]
```

이 구조에서 `busd`는 데이터를 생성하거나 해석하지 않는다. Publisher가 보낸 메시지를 해당 토픽을 구독한 Subscriber에게 중계한다. 각 기능을 별도 프로세스로 나눌 수 있으므로 탐지기, 추적기, UI를 독립적으로 실행하거나 교체할 수 있다.

## 프로세스 구성

### 현재 실행되는 프로세스

1. `argus-busd`는 ZeroMQ XSUB와 XPUB 프록시를 실행한다.
2. `argus-vision`은 카메라, 프레임 큐, 전처리기, Hailo 탐지기와 Publisher를 실행한다.
3. `argus-detection-sub`은 탐지 메시지를 구독해 버스 동작을 확인한다.
4. `argus-preview-sub`은 선택적으로 JPEG 미리보기를 받아 화면에 표시한다.

### 다음 단계에서 추가할 프로세스

1. `tracker-worker`는 `perception/observations`를 구독하고 `tracking/tracks`를 발행한다.
2. `control-worker`는 최신 트랙과 기체 상태를 모아 제어 명령을 계산한다.
3. `command-gateway`는 Windows 명령의 요청 ID를 검사하고 중복 명령을 제거한다.
4. `vehicle-adapter`는 MAVSDK를 통해 PX4 텔레메트리를 받고, 검증된 명령만 전송한다.
5. `recorder`는 탐지, 추적, 상태, 자세와 명령 시간을 비동기로 저장한다.

## 카메라부터 탐지 결과까지의 데이터 흐름

### 카메라 프레임 수신

USB 카메라는 `/dev/video0` 같은 V4L2 장치로 열린다. 실행 프로그램은 해상도, FPS와 FOURCC를 요청하지만 실제 적용값은 카메라가 지원하는 형식에 따라 달라질 수 있다. 따라서 시작 시 실제 수신 프레임의 폭과 높이를 확인해야 한다.

OpenCV가 반환하는 일반적인 프레임은 다음과 같다.

```python
frame.shape == (480, 640, 3)
frame.dtype == np.uint8
```

배열 차원은 높이, 폭, 채널 순서다. 색상 채널은 RGB가 아니라 BGR이다. `frame[0, 0]`은 왼쪽 위 픽셀의 파랑, 초록, 빨강 값을 가진다.

### 최신 프레임 큐

카메라가 30 FPS로 프레임을 만들면 약 33.3 ms마다 새 프레임이 들어온다. 추론이 일시적으로 느려져 모든 프레임을 큐에 쌓으면 처리 중인 영상이 실제 상황보다 점점 늦어진다. 드론 추적에서는 모든 과거 프레임을 처리하는 것보다 현재에 가까운 프레임을 처리하는 편이 중요하다.

현재 `LatestFrameQueue`의 기본 용량은 2다. 큐가 가득 찬 상태에서 새 프레임이 들어오면 가장 오래된 프레임을 버리고 새 프레임을 넣는다. `dropped_frames`는 이렇게 폐기된 프레임 수를 기록한다.

### 640×480에서 640×640으로 전처리

YOLOX HEF 입력이 640×640이고 카메라 프레임이 640×480이면 다음 계산을 사용한다.

```text
scale = min(640 / 640, 640 / 480) = 1.0
resized width = 640
resized height = 480
pad x = 0
pad y = (640 - 480) / 2 = 80
```

원본 영상의 가로세로 비율을 바꾸지 않고 위쪽과 아래쪽에 각각 80픽셀을 채운다. 패딩 픽셀값은 현재 코드에서 114다. 이후 BGR을 RGB로 변환하고 연속된 `uint8` 배열로 만든다.

```text
모델 입력의 논리적 형태 NHWC
배치 1 × 높이 640 × 폭 640 × 채널 3
자료형 uint8
채널 순서 RGB
```

640×480 영상을 강제로 640×640으로 늘리면 객체가 세로로 길어지고 모델 정확도가 떨어질 수 있다. Letterbox는 이런 왜곡을 피한다.

### Hailo 8 입력

HEF는 Hailo Dataflow Compiler가 특정 Hailo 아키텍처에 맞게 만든 실행 파일이다. Raspberry Pi에서 PyTorch나 ONNX 파일을 그대로 Hailo-8에 넣지 않는다. 현재 런타임은 다음 조건의 HEF를 요구한다.

- 입력이 하나여야 한다.
- 입력 채널이 3이어야 한다.
- 입력 형식이 NHWC RGB `uint8`이어야 한다.
- 출력이 하나인 HailoRT NMS 형식이어야 한다.
- HEF의 클래스 수와 `labels.txt` 줄 수가 같아야 한다.
- 현재 구현 기준 HailoRT와 PyHailoRT 버전은 4.23.x다.

실제 입력 폭과 높이는 코드에 고정하지 않고 HEF에서 읽는다. 따라서 다른 크기의 HEF를 사용할 수는 있지만, 학습과 변환 과정에서 사용한 전처리 규칙이 현재 코드와 일치해야 한다.

## 이미 저장된 YOLOX 기본 가중치로 시작하는 방법

결론부터 말하면, 공식 YOLOX 기본 가중치를 사용하면 **학습 단계만 생략**할 수 있다. 다만 보유한 파일이 `.pth`, `.onnx`, `.hef` 중 무엇인지에 따라 시작 지점이 달라진다. Hailo-8은 PyTorch 체크포인트나 ONNX를 직접 실행하지 않으며, 최종적으로 Hailo-8용 `.hef`가 필요하다.

| 이미 가진 파일 | 생략할 수 있는 단계 | PC에서 해야 할 일 | RPi5에서 사용하는 파일 |
|---|---|---|---|
| `yolox_s.pth` | YOLOX 재학습 | ONNX 내보내기, Hailo 파싱, INT8 최적화, Hailo-8 컴파일 | `.hef` |
| `yolox_s.onnx` | 재학습과 ONNX 내보내기 | Hailo 파싱, INT8 최적화, Hailo-8 컴파일 | `.hef` |
| Hailo-8용 `yolox_s.hef` | 학습과 모든 변환 | 입력·출력·라벨 호환성 검사만 수행 | 해당 `.hef` |

즉, 기본 `.pth`를 이미 가지고 있다면 전체 흐름은 다음처럼 짧아진다.

```text
공식 YOLOX COCO 가중치 yolox_s.pth
  → PC에서 ONNX 내보내기
  → PC 또는 Hailo 지원 개발 환경에서 HAR 생성
  → 대표 이미지로 INT8 보정 및 최적화
  → Hailo-8용 HEF 컴파일
  → HEF와 COCO 80 라벨을 RPi5로 복사
  → RPi5의 Hailo-8에서 실행
```

### 경우 1: 공식 YOLOX `.pth`만 있는 경우

YOLOX 공식 저장소에서 제공하는 `yolox_s.pth`, `yolox_tiny.pth` 같은 파일은 일반적으로 COCO 데이터셋으로 학습된 PyTorch 체크포인트다. 새로 학습하지 않고 이 파일을 ONNX로 내보낸 뒤 Hailo 변환을 진행한다. 예를 들어 YOLOX-S를 선택했다면 모델 이름, 체크포인트, 입력 크기를 서로 일치시킨다.

```bash
python tools/export_onnx.py \
  --output-name yolox_s.onnx \
  -n yolox-s \
  -c yolox_s.pth
```

그다음 Hailo Model Zoo 또는 Dataflow Compiler 환경에서 다음 논리 순서를 수행한다.

```text
yolox_s.onnx
  → parse: yolox_s.har
  → optimize/calibrate: yolox_s_quantized.har
  → compile for Hailo-8: yolox_s_coco_hailo8.hef
```

명령의 세부 옵션은 설치된 Hailo Model Zoo와 Dataflow Compiler 버전에 따라 달라질 수 있다. 특히 현재 Hailo Model Zoo의 기본 브랜치는 최신 가속기 중심이며, Hailo-8/Hailo-8L은 호환되는 Model Zoo 2.x와 DFC 3.x 계열을 사용해야 한다. 설치된 HailoRT와 변환 도구의 호환표를 먼저 확인하고, 최신 브랜치의 다른 가속기용 예제를 그대로 복사하지 않는다.

### 경우 2: ONNX까지 이미 있는 경우

`yolox_s.onnx`가 있고 모델 구조와 라벨을 알고 있다면 PyTorch와 YOLOX 내보내기 환경은 더 이상 필요하지 않다. ONNX부터 Hailo 파싱, INT8 최적화, Hailo-8 컴파일을 수행한다. ONNX의 입력 크기, 채널 순서, 정규화 방식과 출력 노드가 Hailo 변환 설정과 맞아야 한다.

### 경우 3: Hailo-8용 HEF까지 이미 있는 경우

HEF가 실제 Hailo-8용이고 현재 프로그램의 계약을 만족하면 변환을 전부 생략한다. 파일을 RPi5의 `models` 폴더에 복사하고 모델과 같은 클래스 순서의 라벨 파일을 지정하면 된다.

```bash
./scripts/run_rpi.sh \
  models/yolox_s_coco_hailo8.hef \
  /dev/video0 \
  config/coco80.txt \
  --preview
```

직접 실행할 때는 메시지 버스를 먼저 시작하고 비전 프로세스를 실행한다.

```bash
argus-busd

argus-vision \
  --profile REAL_IR \
  --backend hailo \
  --hef models/yolox_s_coco_hailo8.hef \
  --labels config/coco80.txt \
  --camera /dev/video0 \
  --width 640 --height 480 --fps 30
```

파일 이름에 `hailo8`이 적혀 있다는 사실만으로 호환성이 보장되지는 않는다. 실행 전에 프로젝트의 하드웨어 검사를 통해 다음 항목을 확인한다.

- Hailo-8용으로 컴파일되었으며 Hailo-8L이나 다른 가속기용이 아니다.
- 입력이 하나이고 RGB `uint8` 형식이다.
- 현재 구현이 요구하는 HailoRT NMS 출력 하나가 들어 있다.
- HEF의 클래스 수와 라벨 파일의 줄 수 및 순서가 같다.
- 컴파일에 사용한 툴체인과 RPi5에 설치한 HailoRT가 호환된다.

### 기본 COCO 가중치가 적합한 경우와 재학습이 필요한 경우

기본 YOLOX 가중치는 보통 COCO 80개 클래스를 탐지한다. 따라서 RGB 카메라로 사람, 자동차, 버스, 트럭, 자전거 등 COCO에 포함된 물체를 먼저 탐지하여 카메라, NPU, 메시지 버스, 추적 흐름을 검증하는 데 적합하다. 이때는 `config/coco80.txt`를 사용해야 한다.

반면 드론, 특정 군용·산업용 차량, 사용자가 정의한 표적 또는 열화상 전용 표적처럼 COCO에 없거나 영상 특성이 크게 다른 대상은 기본 가중치만으로 안정적인 결과를 기대하기 어렵다. 이 경우 기본 체크포인트를 초기값으로 사용해 사용자 데이터로 미세조정한 뒤 ONNX와 HEF를 다시 만든다. 라벨 이름만 바꿔서는 모델이 새 물체를 배우지 않는다.

### 640×480 카메라와 기본 640×640 YOLOX 모델

카메라가 640×480이고 HEF 입력이 640×640이어도 사용할 수 있다. 현재 전처리기는 비율을 유지한 채 위아래에 각각 80픽셀을 채우는 Letterbox를 수행한다. 따라서 카메라를 억지로 640×640으로 늘릴 필요는 없다. 다만 INT8 보정 이미지는 실제 운용 카메라와 비슷한 조명, 거리, 배경을 포함해야 양자화 후 정확도 저하를 줄일 수 있다.

### Hailo 8 출력

현재 코드는 NMS가 포함된 HEF를 사용한다. NMS는 같은 객체 주변에 겹쳐 나온 후보 박스 중 대표 박스를 남기는 후처리다. NPU 출력은 논리적으로 클래스별 탐지 목록이며, 각 탐지는 다음 다섯 값으로 해석한다.

```text
[ymin, xmin, ymax, xmax, confidence]
```

좌표는 보통 모델 입력 크기에 대한 0부터 1 사이의 정규화 값이다. `confidence`가 설정한 임계값보다 낮으면 버린다. 현재 기본 임계값은 0.35다.

Raw YOLOX 출력만 가진 HEF는 여러 특징맵을 반환하며 CPU 디코딩과 NMS가 별도로 필요하다. 현재 `HailoNmsDetector`는 이런 HEF를 받지 않고 시작 단계에서 오류를 낸다. 첫 구현에서는 NMS 포함 HEF를 사용해 출력 경계를 단순하게 유지한다.

### 원본 좌표 복원

NPU 좌표는 640×640 Letterbox 영상 기준이다. UI와 추적기는 640×480 원본 영상 기준 좌표를 사용해야 한다. 현재 코드는 다음 식으로 좌표를 복원한다.

```text
x source = (x normalized × model width - pad x) / scale
y source = (y normalized × model height - pad y) / scale
```

640×480 예에서는 `scale`이 1이고 `pad y`가 80이므로 모델 좌표의 y값에서 80을 뺀 결과가 원본 y좌표가 된다. 복원 결과는 원본 영상 범위 안으로 제한한다.

### 전체 박스 보존

탐지기가 원본 영상 좌표로 복원한 `x1, y1, x2, y2` 전체 박스를 그대로 발행한다. 표시·추적·선택·기하 계산은 이 전체 박스를 기준으로 하며 하단 ROI를 생성하지 않는다. 중심은 `((x1+x2)/2, (y1+y2)/2)`, 크기는 `(x2-x1, y2-y1)`이다.

## NPU 입력과 출력 예시

640×480 카메라에서 한 프레임을 받았다고 가정한다.

### 입력 예시

```text
카메라 배열        shape 480 640 3  BGR uint8
Letterbox 배열     shape 640 640 3  RGB uint8
NPU 배치           shape 1 640 640 3  NHWC
```

### 출력 예시

```text
class id 0
ymin 0.234
xmin 0.156
ymax 0.781
xmax 0.625
confidence 0.92
```

모델 좌표와 원본 좌표를 계산하면 다음과 같다.

```text
x1 model = 0.156 × 640 = 100
y1 model = 0.234 × 640 = 150
x2 model = 0.625 × 640 = 400
y2 model = 0.781 × 640 = 500

x1 source = 100
y1 source = 150 - 80 = 70
x2 source = 400
y2 source = 500 - 80 = 420
```

최종 Detection은 원본 640×480 화면에서 `(100, 70, 400, 420)` 박스를 가진다.

## 메시지 버스 구조

### ROS 2 없이 동작하는 이유

Hailo-8, OpenCV와 YOLOX는 ROS 2에 의존하지 않는다. 프로세스 사이의 데이터 전달 규칙만 다른 방법으로 제공하면 된다. 현재 시스템은 ZeroMQ의 Publish Subscribe 패턴과 MessagePack 직렬화를 사용한다.

ROS 2를 사용하지 않으면 설치와 실행 구성이 단순해지는 대신 토픽 규칙, 메시지 버전, 시간, 재연결, 상태 감시, 기록, 명령 응답과 보안을 프로젝트가 직접 관리해야 한다. 이 문서의 메시지 계약과 안전 규칙은 그 책임을 코드에 명시하기 위한 기준이다.

### busd 연결 구조

```text
Publisher들 ── connect tcp 127.0.0.1 5555 ──┐
                                             │
                                      ZeroMQ busd
                                             │
Subscriber들 ─ connect tcp Pi주소 5556 ──────┘
```

`busd`의 Publisher 입력은 기본적으로 Raspberry Pi의 loopback에만 열고, Subscriber 출력은 Windows 통제기가 접속할 수 있도록 외부 인터페이스에 연다. 현재 버스에는 인증과 암호화가 없으므로 개발용 격리 네트워크와 방화벽을 사용해야 한다.

### 전송 프레임

버스 메시지는 ZeroMQ multipart 형식이다.

| 순서 | 내용 | 형식 | 설명 |
|---|---|---|---|
| 1 | topic | UTF 8 문자열 | 구독 필터에 사용 |
| 2 | header | MessagePack map | 스키마와 구조화 데이터 |
| 3 | payload | 선택적 bytes | JPEG 같은 큰 이진 데이터 |

일반 탐지 메시지는 첫 번째와 두 번째 프레임만 사용한다. JPEG 미리보기는 세 번째 프레임에 압축 영상 바이트를 넣는다. 구조화 헤더와 큰 이진 데이터를 분리하면 JSON 문자열에 이미지를 넣는 방식보다 복사와 크기 증가를 줄일 수 있다.

### 큐와 실시간 정책

Publisher는 non blocking 전송을 사용하고 송신 High Water Mark 기본값은 4다. Subscriber 수신 High Water Mark 기본값은 8이다. 느린 구독자 때문에 카메라와 추론이 멈추지 않도록, 큐가 가득 찬 상황에서는 오래된 메시지를 보존하기보다 최신 데이터를 우선한다.

이 정책은 실시간 상태 데이터에 적합하지만 모든 메시지를 반드시 보존해야 하는 감사 로그에는 적합하지 않다. Recorder는 별도 저장 큐와 유실 계수를 가져야 한다.

## 토픽 계약

| 토픽 | 스키마 | 생산자 | 소비자 | 상태 |
|---|---|---|---|---|
| `perception/observations` | `argus.perception.observations.v1` | Perception Worker | Tracker, 시험 구독자 | 구현됨 |
| `vision/overlay/jpeg` | `argus.vision.overlay.v1` | Overlay Encoder | Windows UI, 미리보기 | 구현됨 |
| `diagnostics/events` | `argus.diagnostics.event.v1` | 카메라와 탐지기 등 | Health, Status | 기본 구현됨 |
| `tracking/tracks` | `argus.tracking.tracks.v1` | Tracker | Store, UI, Recorder | 계약 정의, 워커 미구현 |
| `system/status` | `argus.system.status.v1` | Control과 Health | UI, Recorder | 다음 단계 |
| `command/request` | `argus.command.request.v1` | Command Gateway | ControlLoop | 다음 단계 |
| `command/result` | `argus.command.result.v1` | ControlLoop | Command Gateway | 다음 단계 |

영상과 명령은 같은 전달 정책을 사용하면 안 된다. 미리보기 영상은 일부 프레임이 유실되어도 다음 프레임으로 회복할 수 있다. 반면 추종 시작과 정지 명령은 요청 ID, 중복 제거, 처리 결과와 만료 시간이 필요하다. 따라서 최종 시스템에서는 데이터 스트림과 명령 채널을 분리한다.

## 주요 데이터 구조

### CapturedFrame

카메라 스레드와 추론 루프 사이에서 사용하는 프로세스 내부 구조다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `frame_id` | integer | 카메라 시작 후 증가하는 프레임 번호 |
| `image` | NumPy uint8 array | OpenCV BGR 원본 프레임 |
| `captured_unix_ns` | integer | 기록과 외부 표시용 벽시계 시간 |
| `captured_monotonic_ns` | integer | 동일 장치 내부 지연 계산용 단조 시간 |

### Detection

객체 하나를 표현한다. 좌표는 원본 카메라 픽셀 기준이다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `class_id` | integer | HEF 클래스 인덱스 |
| `label` | string | `labels.txt`에서 읽은 이름 |
| `confidence` | float | 0부터 1 사이 탐지 신뢰도 |
| `x1 y1 x2 y2` | integer | 전체 박스의 왼쪽 위와 오른쪽 아래 좌표 |
| `track_id` | integer 또는 null | Tracker가 할당할 지속 ID |

### DetectionFrame

한 영상 프레임의 모든 탐지를 묶어 `perception/observations`로 발행한다.

| 필드 | 의미 |
|---|---|
| `schema` | 메시지 호환성을 구분하는 버전 문자열 |
| `source` | `camera:/dev/video0` 같은 입력 출처 |
| `frame_id` | 원본 프레임 식별자 |
| `captured_unix_ns` | 기록용 절대 시간 |
| `captured_monotonic_ns` | 장치 내부 지연 계산 시작점 |
| `published_monotonic_ns` | 메시지 발행 시점 |
| `image_width image_height` | 좌표가 기준으로 삼는 원본 해상도 |
| `model` | 사용한 HEF 파일 이름 또는 mock 모델 이름 |
| `inference_ms` | 탐지기 호출에 걸린 시간 |
| `coordinate_frame` | 기본값 `camera_pixel` |
| `observation_kind` | 기본값 `IMAGE2D` |
| `detections` | Detection 목록 |

예시 메시지는 다음과 같다.

```json
{
  "schema": "argus.perception.observations.v1",
  "source": "camera:/dev/video0",
  "frame_id": 42,
  "captured_unix_ns": 1789980000000000000,
  "captured_monotonic_ns": 502100000000,
  "published_monotonic_ns": 502112500000,
  "image_width": 640,
  "image_height": 480,
  "model": "yolox_s_640_target_v01_hailo8.hef",
  "inference_ms": 4.1,
  "coordinate_frame": "camera_pixel",
  "observation_kind": "IMAGE2D",
  "detections": [
    {
      "class_id": 0,
      "label": "target",
      "confidence": 0.92,
      "x1": 100,
      "y1": 70,
      "x2": 400,
      "y2": 420,
      "track_id": null
    }
  ]
}
```

`pipeline_latency_ms`는 `(published_monotonic_ns - captured_monotonic_ns) / 1000000`으로 계산한다. 서로 다른 컴퓨터의 monotonic 시간을 직접 비교하면 안 된다. Windows와 Raspberry Pi 사이의 절대 시간 비교가 필요하면 시간 동기화 방식과 오차를 별도로 관리해야 한다.

## 탐지 이후의 추적 구조

탐지는 프레임마다 독립적으로 나온다. 같은 사람이라도 다음 프레임에서는 새 탐지 결과일 뿐이다. Tracker는 여러 프레임의 위치와 운동을 연결해 같은 객체에 지속적인 `track_id`를 부여한다.

```text
프레임 100 Detection 사람 박스
프레임 101 Detection 사람 박스  ── Tracker ── Track ID 7
프레임 102 잠시 미탐지                  Predicted
프레임 103 다시 탐지                    Confirmed ID 7
```

권장 기본 Tracker는 ByteTrack이며 ReID는 첫 단계에서 사용하지 않는다. 카메라가 기체와 함께 움직이므로 FC의 Roll, Pitch, Yaw를 프레임 시각에 보간해 Camera Motion Compensation에 사용할 계획이다. 비교 실험은 OC SORT 또는 CMC 비활성 조합으로 수행할 수 있다.

Track 메시지에는 다음 정보가 필요하다.

- `track_id`, 클래스와 신뢰도
- full box
- full box 중심점과 크기
- `Confirmed`, `Predicted`, `Lost` 상태
- 마지막 관측 시각과 TTL
- 좌표계와 출처
- 필요 시 픽셀 속도와 예측 위치

## 표적 선택과 제어 구조

운용자가 Windows 통제기에서 한 개의 Track ID를 지정하면 `TargetSelector`가 그 ID를 고정한다. 박스가 겹쳐도 자동으로 다른 ID로 바꾸지 않는다. 지정 표적이 일시적으로 보이지 않으면 Tracker의 Predicted 상태를 짧은 TTL 동안 사용할 수 있지만, TTL을 넘기면 제어 입력으로 사용하지 않는다.

제어 경로는 다음 순서를 따른다.

```text
tracking tracks
    ↓
LatestStateStore
    ↓
ControlContext 한 시점의 스냅샷
    ↓
TargetSelector와 Geometry
    ↓
MissionStateMachine
    ↓
Follower가 ControlIntent 생성
    ↓
CommandGuard가 권한 한도 신선도 검사
    ↓
MavsdkVehicleAdapter 단일 송신자
    ↓
PX4
```

`CommandGuard`는 제어권, RC 오버라이드, 속도와 각도 한도, 명령 만료, stale 데이터와 통신 상태를 확인해야 한다. Hover와 정지는 일반 추종 명령보다 높은 우선순위를 가져야 한다. MAVLink 송신자는 하나만 두어 서로 다른 프로세스가 충돌하는 명령을 보내지 않게 한다.

## 환경 프로파일

Composition Root는 환경 프로파일을 읽고 실제 구현체를 선택한다.

| 프로파일 | 입력 | 탐지 | 추적 | Vehicle Port |
|---|---|---|---|---|
| `SITL_POSE` | Gazebo 좌표 | 사용하지 않음 | Pose 기반 | MAVSDK UDP |
| `SITL_IMAGE` | Gazebo 카메라 | PC YOLOX | ByteTrack CMC | MAVSDK UDP |
| `REAL_IR` | 현재는 V4L2 카메라 | Hailo YOLOX | ByteTrack CMC | MAVSDK Serial |
| `REPLAY` | 영상과 FC 로그 | Hailo YOLOX | ByteTrack CMC | Replay |

프로파일 이름 `REAL_IR`는 원래 열상 카메라 구성을 반영한다. 현재 RGB 카메라 시험에서도 같은 V4L2 경로를 재사용할 수 있으나, 장기적으로 `REAL_RGB` 프로파일을 추가하면 구성 의도가 더 분명해진다.

## 실제 실행 순서

### 최초 설치

Raspberry Pi에서 프로젝트 폴더로 이동한 뒤 설치 스크립트를 실행한다.

```bash
cd argus_vision_bus
bash scripts/setup_rpi.sh
sudo reboot
```

Hailo-8용 YOLOX HEF를 `models` 폴더에 복사하고 `config/labels.txt`를 모델 클래스 순서와 맞춘다.

### 장치와 모델 확인

640×480 카메라를 기준으로 다음 명령을 사용한다.

```bash
./scripts/verify_rpi.sh /dev/video0 \
  models/yolox_s_640_target_v01_hailo8.hef \
  config/labels.txt
```

스크립트 기본 해상도가 다른 경우 수동 검사 명령 또는 실행 옵션에서 `--width 640 --height 480`을 명시한다. 실제 카메라 지원 형식은 다음 명령으로 확인한다.

```bash
v4l2-ctl --device /dev/video0 --list-formats-ext
```

### Hailo 없이 버스 시험

세 개의 터미널에서 순서대로 실행한다.

```bash
# 터미널 1
argus-busd

# 터미널 2
argus-detection-sub

# 터미널 3
argus-vision --backend mock --camera /dev/video0 \
  --width 640 --height 480 --labels config/labels.txt
```

이 시험은 카메라, 큐와 버스를 먼저 검증한다. MockDetector는 움직이는 가짜 박스를 만들기 때문에 HEF와 Hailo 장치가 없어도 전체 메시지 경로를 확인할 수 있다.

### 실제 Hailo 실행

```bash
argus-busd
```

다른 터미널에서 다음을 실행한다.

```bash
argus-vision \
  --profile REAL_IR \
  --backend hailo \
  --hef models/yolox_s_640_target_v01_hailo8.hef \
  --labels config/labels.txt \
  --camera /dev/video0 \
  --width 640 --height 480 --fps 30 \
  --fourcc MJPG \
  --score-threshold 0.35 \
  --frame-queue-size 2
```

로컬 화면에서 박스가 그려진 JPEG를 확인하려면 `--publish-preview`를 추가하고 `argus-preview-sub`을 실행한다.

### Windows에서 구독

Windows 구독자는 Raspberry Pi의 IP 주소와 Subscriber 포트에 연결한다.

```text
tcp://192.168.0.20:5556
```

방화벽은 Windows 통제기 주소 또는 운용 전용 서브넷만 허용하는 것이 좋다. 현재 상태에서 인터넷이나 공용 네트워크에 5556 포트를 직접 노출하지 않는다.

## 상태와 오류 처리

### 카메라

- 시작 시 장치 열기 실패를 즉시 오류로 처리한다.
- 연속으로 빈 프레임 10개를 받으면 fault를 발행하고 종료한다.
- 실제 적용된 해상도, FPS와 픽셀 형식을 상태에 기록하는 기능을 추가하는 것이 좋다.
- 재연결 기능은 다음 단계에서 제한된 횟수와 backoff를 두고 구현한다.

### Hailo 8과 HEF

- `hailortcli fw-control identify`로 Hailo-8인지 확인한다.
- Hailo-8L을 Hailo-8용 프로파일로 잘못 사용하는 경우 시작을 거부한다.
- HEF 입력 개수, 채널, 자료형과 NMS 출력 형식을 시작 전에 검사한다.
- 라벨 수가 모델 클래스 수와 다르면 시작을 거부한다.
- NPU 온도, 전원 상태와 추론 오류를 주기적으로 `diagnostics/events`에 발행하는 기능이 필요하다.

### 버스

- Subscriber는 메시지의 `schema`를 확인해야 한다.
- 알 수 없는 버전은 조용히 잘못 해석하지 말고 거부하거나 호환 어댑터를 사용한다.
- 실시간 토픽은 오래된 데이터 폐기를 허용한다.
- 명령은 처리 결과가 올 때까지 요청 ID로 추적한다.
- Heartbeat가 끊기면 UI는 연결 끊김을 표시하고 제어기는 안전 상태로 전환한다.

### 제어 안전

탐지와 영상 표시가 정상이어도 바로 비행 명령을 보내면 안 된다. 다음 조건을 모두 만족한 경우에만 Follower 출력을 통과시킨다.

- 운용자가 추종 시작을 명시했다.
- 선택한 Track ID가 유효하고 TTL 안에 있다.
- FC 텔레메트리가 최신이다.
- RC 수동 우선권과 비상 정지가 활성화되지 않았다.
- 계산된 명령이 속도, 각도와 고도 한도 안에 있다.
- GCS 또는 내부 watchdog 정책이 허용 상태다.

## 성능을 볼 때의 기준

FPS 하나만 보면 시스템 지연을 놓칠 수 있다. 다음 값을 함께 기록해야 한다.

| 항목 | 계산 또는 의미 |
|---|---|
| Camera FPS | 카메라가 실제로 전달한 초당 프레임 수 |
| Inference ms | Hailo 탐지기 호출 시간 |
| Pipeline age ms | 캡처부터 Observation 발행까지의 시간 |
| Dropped frames | 최신 프레임 정책으로 폐기한 수 |
| Detection count | 프레임별 탐지 수와 분포 |
| Tracking retention | 지정 표적 ID가 유지된 비율 |
| Command age | 프레임 시각부터 제어 명령 생성까지의 시간 |
| End to end latency | 카메라 캡처부터 실제 기체 반응 또는 UI 표시까지의 시간 |

성능 목표값은 하드웨어, 모델 크기와 제어 요구를 측정한 뒤 확정해야 한다. 초기 시험에서는 640×480 30 FPS 입력, 큐 크기 2, 미리보기 비활성 상태를 기준으로 측정하는 것이 좋다. JPEG 인코딩과 네트워크 미리보기는 CPU와 대역폭을 추가로 사용하므로 탐지 성능 시험과 분리한다.

## 시험 체크리스트

### 카메라 시험

- [ ] `/dev/video0` 장치가 존재한다.
- [ ] 640×480 30 FPS 형식을 지원한다.
- [ ] 실제 프레임이 `(480, 640, 3)`으로 수신된다.
- [ ] BGR과 RGB 변환 결과의 색상이 정상이다.

- [ ] Hailo-8이 Hailo-8L이 아닌 정확한 장치로 식별된다.
- [ ] HailoRT와 PyHailoRT 버전이 일치한다.
- [ ] HEF 입력이 단일 RGB `uint8`이다.

- [ ] 좌표 복원 결과가 원본 영상의 객체와 일치한다.
- [ ] 빈 화면과 다중 객체 화면에서 오류가 없다.

### 버스 시험

- [ ] busd보다 먼저 시작한 Publisher와 Subscriber가 재연결한다.
- [ ] 토픽 필터가 다른 메시지를 섞지 않는다.
- [ ] 느린 Subscriber가 Vision Worker를 멈추지 않는다.
- [ ] schema가 다른 메시지를 검출한다.

- [ ] 네트워크 단절 후 상태를 표시한다.

- [ ] 장시간 실행 중 메모리가 계속 증가하지 않는다.
- [ ] `pipeline age ms`가 누적 증가하지 않는다.

- [ ] RC override가 자동 제어보다 우선한다.
- [ ] Heartbeat 단절 시 Hover 또는 사전에 정한 안전 상태로 이동한다.

- [ ] MAVLink 명령 송신자가 하나뿐이다.

## 자주 발생하는 문제

### 카메라가 640×480으로 열리지 않음

카메라가 요청한 FOURCC와 FPS 조합을 지원하지 않을 수 있다. `v4l2-ctl`로 지원 목록을 확인하고 `MJPG`와 `YUYV`를 각각 시험한다. 프로그램이 요청한 값이 아니라 실제 프레임 크기를 로그로 확인한다.

### 화면 색상이 이상함

OpenCV 입력은 BGR인데 모델은 RGB를 기대한다. BGR to RGB 변환이 빠졌거나 두 번 적용되었는지 확인한다.

### 박스 y 좌표가 위아래로 어긋남

640×480을 640×640으로 만들 때 들어간 상하 80픽셀 패딩을 좌표 복원에서 빼지 않았을 가능성이 크다. HEF 입력 크기가 실제로 640×640인지도 확인한다.

### 탐지가 전혀 나오지 않음

라벨 파일 문제만으로 탐지가 사라지지는 않지만, 모델 전처리와 현재 코드의 전처리가 다르면 결과가 크게 나빠질 수 있다. RGB 순서, `uint8`, Letterbox 방식, 패딩값 114, 입력 크기와 모델 변환 설정을 확인한다. 임계값 0.35를 시험 목적으로 낮춰 raw 경향을 볼 수 있지만 운용값은 평가 후 정한다.

### HEF 출력 개수 오류

현재 코드는 NMS 출력 하나를 기대한다. Raw YOLOX 특징맵 HEF를 사용하면 여러 출력이 나타날 수 있다. Hailo 모델 변환 단계에서 NMS를 포함하거나 별도 Raw 출력 디코더를 구현해야 한다.

### FPS는 높은데 화면이 늦음

카메라 또는 애플리케이션 큐에 과거 프레임이 쌓였을 수 있다. OpenCV 버퍼 크기 1, LatestFrameQueue 용량 2와 오래된 프레임 폐기 여부를 확인한다. FPS와 함께 pipeline age를 본다.

## 최종 권장 기준 구성

첫 실제 장비 시험은 다음 구성으로 시작한다.

```text
Raspberry Pi 5 64 bit OS와 능동 냉각
Hailo 8과 HailoRT PyHailoRT 4.23.x
USB RGB 카메라 640×480 30 FPS MJPG
YOLOX 640×640 RGB uint8 NMS 포함 Hailo 8 HEF
프레임 큐 2
탐지 임계값 0.35 시작 후 데이터로 조정
ZeroMQ XSUB XPUB와 MessagePack
원본 영상은 로컬 처리
Windows에는 탐지 데이터와 저율 JPEG만 전송
추적과 제어를 붙이기 전 카메라 NPU 버스를 각각 검증
```

이 구성은 현재 코드와 가장 잘 맞으며, Hailo 없이 MockDetector로 먼저 버스를 확인한 뒤 실제 HEF를 연결할 수 있다. 추적과 제어 기능을 추가할 때도 `DetectionFrame`과 토픽 계약을 유지하면 인지 코드를 크게 바꾸지 않고 다음 워커를 붙일 수 있다.
